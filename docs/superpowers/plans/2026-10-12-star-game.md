# 별 키우기 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. 사용자에게 병렬 에이전트 실행을 별도로 위임받은 경우 superpowers:subagent-driven-development를 사용할 수 있다. 아래 체크박스는 실제 증거를 얻은 뒤 표시한다.

**Goal:** 픽셀 감성의 무료·광고 포함 별 키우기 Android 게임을 구현하고, 제품 명세의 `RELEASE_READY` 조건까지 충족한다. 게임 진행은 오프라인에서도 가능하다.

**Architecture:** Android 앱 모듈 하나, 순수 Kotlin 게임 규칙, DataStore 저장소 하나, ViewModel 하나와 Compose 화면 3개, 배너 광고·동의 연동을 사용한다. 생산은 경과 시간으로 계산하며 백그라운드 프로세스는 사용하지 않는다. 서버 로그인·복구는 후속 단계다.

**Tech Stack:** Kotlin, Jetpack Compose, AndroidX ViewModel/Lifecycle, DataStore, kotlinx.serialization, Google Mobile Ads SDK·UMP(권장안), Gradle Kotlin DSL, JUnit, Compose UI Test, Git. 정확한 호환 버전은 M0/M3a에서 검증·고정한다.

**Spec:** [게임 방향과 제품 명세](../specs/2026-10-12-star-game-design.md)

작성일: 2026-10-12 · 현재 상태: 계획만 작성됨. 이 문서에 나오는 앱·테스트·배포 파일은 앞으로 만들 산출물이다.

## Global Constraints

- 작업 위치는 `C:/Users/PC/Projects/ZeroStar`다. `C:/Users/PC/Desktop/zeroverse-server`는 디자인 읽기 참고로만 사용한다.
- 재화 1종, 강화 1종/최대 30레벨, 성장 6단계, 도감 6종, 오프라인 최대 8시간/100% 생산.
- 한국어·무료·광고 포함·인앱결제 없음. 초기 로그인·자체 게임 서버 없음. 별도 분석 SDK, 알림, 자동화 서비스 추가 금지.
- 광고 기본안은 AdMob 홈 하단 배너 1개. 광고 상태가 게임 경제·로컬 저장을 바꾸지 않으며 광고 요청 불가·오프라인에도 플레이 가능해야 한다.
- 후속 DB 서버 로그인·복구는 제품 명세 §12에 따라 별도 구현한다. 초기 출시에는 서버용 빈 코드나 임시 로그인 UI를 넣지 않는다.
- `minSdk = 26`, `targetSdk = 36`, `compileSdk >= 36`. 제출 시점 정책이 더 높으면 올리고 회귀 테스트한다.
- 게임 규칙 수치는 명세 §4가 정본이다. 조정 시 명세·코드·테스트·시뮬레이션 결과를 같은 작업에서 갱신한다.
- 단일 앱 모듈을 유지한다. 패키지 분리만 사용하고 DI 프레임워크·Room·게임 엔진을 도입하지 않는다.
- 사용자 비밀, 키스토어, 암호, 로컬 SDK 경로, 기기 식별자를 공개 Git이나 배포 문서에 넣지 않는다.
- 개발 중 임시 applicationId는 `com.example.zerostar`, Kotlin namespace는 `com.zerostar.game`. 첫 스토어 업로드 전 사용자 확정 applicationId로 교체한다. 임시 ID로 Play 앱을 만들지 않는다.
- Git 사용은 확정이다. M0에서 저장소를 확인/초기화하고 검증 단위로 커밋한다. 릴리스는 커밋/태그로 고정한다. 원격 URL·공개 범위·접근 권한은 사용자 준비 사항이며 원격 생성·공개 전환을 임의로 실행하지 않는다.

**파일:** 빌드 관련 파일, Manifest, MainActivity, `ui/StarApp.kt`, `.gitignore`, README, `docs/progress.md`.

**입력:** 제품 명세, 확보 가능한 JDK·SDK·에뮬레이터. **출력:** 기기에 설치되는 홈 셸과 재현 가능한 빌드 명령.

- [ ] SDK·Android Studio·adb·JDK를 검색하고 공식 호환 문서로 버전을 선택한다. 현재 조사에서는 JDK 21과 Git/Node가 확인되었고 SDK·Studio는 기본 경로에 없었으며 adb는 PATH에 없었다. 다른 경로의 설치 여부를 먼저 확인한다.

## M1. 순수 게임 규칙과 경제 검증

**파일:** `game/GameState.kt`, `game/GameRules.kt`; 테스트 `GameRulesTest.kt`, `EconomySimulationTest.kt`; `docs/qa/BALANCE.md`.

**인터페이스:**

- `GameState`: 명세 §7의 필드와 초기값을 갖는 불변 직렬화 모델.
- `productionMilliPerSecond(state: GameState): Long`.
- `upgradeCostMilli(level: Int): Long` — 0~29만 허용, 이외 입력 명시적 거부.
- `advance(state: GameState, elapsedSeconds: Long): GameState` — 음수 시간 거부, 종료 상태에서는 변화 없음, 포화 연산.
- `buyUpgrade(state: GameState): GameState` — 구매 불가이면 동일 상태 반환.
- `registerStar(state: GameState): GameState` — 미완성·도감 완료이면 동일 상태, 성공 시 명세의 초기화/엔딩 규칙.
- `stageOf(earnedMilli: Long): Int` — 0~5.

시간 획득·기준 시각 갱신은 M2가 담당하고 규칙 함수는 시스템 시각·Android API를 직접 읽지 않는다.

- [ ] 아래 핵심 assertion을 실패하는 테스트로 작성하고 `./gradlew.bat :app:testDebugUnitTest --tests '*GameRulesTest'`에서 실제 실패를 확인한다.

```kotlin
assertEquals(1_000L, productionMilliPerSecond(initial))
assertEquals(20_000L, upgradeCostMilli(0))
assertEquals(60_000L, advance(initial, 60).balanceMilli)
assertEquals(0L, buyUpgrade(initial.copy(balanceMilli = 20_000)).balanceMilli)
assertEquals(1, buyUpgrade(initial.copy(balanceMilli = 20_000)).upgradeLevel)
assertEquals(initial, buyUpgrade(initial))
assertEquals(5, stageOf(500_000_000L))
```

- [ ] 가장 작은 구현으로 테스트를 통과시킨다. 구매가 `earnedMilli`를 차감하지 않는지, 가격 배열의 모든 값과 최대 레벨을 검사한다.
- [ ] 각 단계의 직전/정확한 경계, Long 상한, 음수 경과 거부, 5번째 등록의 초기화와 6번째 등록의 종료·재등록 불가를 추가 검사한다.
- [ ] 첫 회차 즉시 구매 시뮬레이션에서 최초 강화 20초, 완성 8,501초를 재현한다. 틱 순서는 ‘1초 생산 → 완료 검사 → 살 수 있는 강화 반복’으로 고정한다.
- [ ] ‘처음 180초 동안 즉시 구매, 이후 4시간/8시간마다 복귀해 가능한 강화 일괄 수행, 완성 시 즉시 등록’ 두 시나리오에서 6종 완성까지 각각 158,580초/316,980초를 재현한다. 12시간 간격도 추가 측정한다. 앱에는 일괄 구매 UI를 추가하지 않는다.
- [ ] 일반적인 하루 2~4회 접속에서 약 3~7일 목표와 큰 차이가 있으면 수치를 조정하고 기대값·명세·결과를 일치시킨다. 하루 6회 접속의 4시간 시나리오는 조기 완성을 허용한다. 플레이 감각은 M4 사용자 테스트로 별도 확인한다.
- [ ] `./gradlew.bat :app:testDebugUnitTest` 성공과 BALANCE.md 결과를 기록한다.

## M2. 저장과 생명주기

**파일:** `data/GameRepository.kt`, `data/GameSerializer.kt`, `ui/GameViewModel.kt`, Manifest·백업 XML; 테스트 `GameRepositoryTest.kt`, `LifecycleSaveTest.kt`.

**인터페이스:** `GameRepository.state: Flow<GameState>`; `suspend resume(nowEpochMs: Long): ResumeResult`; `suspend dispatch(action: GameAction, elapsedSeconds: Long, nowEpochMs: Long): SaveResult`.

`GameAction`은 `Checkpoint`, `BuyUpgrade`, `RegisterStar`, `SetSound(enabled)`, `SetReduceMotion(enabled)`, `MarkTutorialSeen`, `Reset`만 둔다. `ResumeResult`는 저장 성공 상태와 지급량/적용 시간 또는 읽기·쓰기 오류다. `SaveResult`는 성공 상태 또는 오류다. `Reset`은 과거 시간 정산 없이 초기 상태와 현재 시각을 저장한다. 다른 액션은 먼저 경과분 정산 후 적용한다.

- [ ] fake clock·임시 디렉터리로 저장소 테스트를 먼저 작성한다. `resume` 3,600초→3,600별빛, 86,400초→28,800별빛, 같은 시각 재호출→추가 0, 역행→0을 검증한다.
- [ ] DataStore 단일 인스턴스의 원자적 갱신과 하나의 직렬 명령 경로를 구현한다. 별도의 자체 DB·파일 잠금 프레임워크는 만들지 않는다.
- [ ] 전경 계산은 monotonic clock, 복귀는 epoch clock을 사용한다. 전경 투영과 저장 기준점이 같은 시간을 두 번 더하지 않도록 30초 체크포인트 전후 테스트를 작성한다.
- [ ] 구매 2회 동시 요청에 1회분 잔액만 있을 때 레벨 +1, 등록 2회 요청에 도감 +1, 복귀와 구매가 겹쳐도 보상은 구매 전 생산량으로 한 번만 반영됨을 검증한다.
- [ ] 파일 없음은 새 게임, 손상·미래 schemaVersion·잘못된 범위·쓰기 실패는 보존+오류임을 검사한다. 오류 시 성공 UI를 표시하지 않고 재시도로 복구할 수 있는지 확인한다.
- [ ] 설정 변경·등록·구매는 저장 완료 뒤 UI에 성공을 표시한다. Android 백그라운드 진입·재시작·강제 종료 시나리오를 연결한다.
- [ ] `./gradlew.bat :app:testDebugUnitTest :app:connectedDebugAndroidTest`로 결과를 남긴다. 강제 종료·재부팅은 별도 adb 시나리오와 실제 기기 기록을 남긴다.

**통과:** 유효한 저장을 조용히 초기화하거나 중복 지급하는 경로가 없다. 백그라운드 서비스 없이 복귀가 동작한다.

## 진행 기록과 재개 규칙

`docs/progress.md`에는 현재 상태, 완료 M단계, 진행 중 작업, 다음 실행할 명령, 차단 사유, 사용자에게 필요한 단일 행동, 마지막 검증 빌드와 증거 경로를 기록한다. 결과를 보지 않고 체크박스를 채우지 않는다.

새 세션은 README → 제품 명세 → 이 계획 → progress → 최신 테스트 증거 순으로 읽는다. 앞 단계 통과가 유효하면 다시 처음부터 기획하지 않는다. 변경 영향이 있는 검증만 재실행한다. 서명·패키지·게임 규칙·저장 구조 변경은 연결된 검증을 반드시 다시 한다.

각 단계 통과 후 해당 변경만 Git에 커밋하고 progress에 커밋과 검증 결과를 남긴다. 키·암호·SDK 캐시·빌드 산출물이 stage되지 않았는지 확인한다. 사용자 지정 원격이 준비되면 위임 범위에서 push하며 로컬 커밋과 원격 백업의 상태를 구분한다.

작업량 예상은 M0~M3 4~8일, 광고 M3a 1~3일, M4~M6 4~7일, 합계 9~18개 작업일을 초기 예약 범위로 둔다. 숙련도·도구·기기·결함에 따라 달라지는 일정 가정이며 에이전트 실행시간 보장이 아니다. 해당 계정의 비공개 테스트는 안정된 테스트 빌드가 나온 후 시작하며 최소 14일과 액세스 검토 시간을 별도로 확보한다. 광고 계정/앱 검토도 별도 대기 요인이다. 3~5주보다 여유 있는 출시 창을 잡고 고정 공개일을 먼저 약속하지 않는다. 후속 DB 서버 로그인·복구의 일정은 이 추정에 포함하지 않는다.
