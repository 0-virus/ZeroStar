# 별 키우기 게임 방향과 제품 명세

작성일: 2026-10-12 · 프로젝트: ZeroStar · 상태: 구현 전 기본안. 사용자 추가 결정: 광고 포함·초기 로컬 저장/후속 서버 로그인 및 복구·Git 보관 반영.

## 1. 목적과 범위

짧게 접속해 별의 변화를 보고, 다시 접속할 이유를 얻는 작은 수집형 방치 게임을 만든다. 에이전트가 구현부터 Android 품질 검증, 배포 파일과 스토어 자료 준비까지 수행할 수 있도록 결정을 구체화한다. 사용자의 이번 요청은 계획 및 문서화이며 제품 코드 구현은 다음 작업이다.

| 구분 | 내용 |
| --- | --- |
| 사용자 확정 조건 | 별 키우기, 방치형, ZeroVerse 프론트의 픽셀 느낌, 간단한 구현, Android 출시 준비, 무료·무결제·광고 포함, 초기 로컬 저장/후속 서버 로그인·복구, Git 보관 |
| 기본 대상 | 하루 2~4회, 한 번에 30초~3분 접속하는 캐주얼 이용자 |
| 기본 배포안 | 한국어, 대한민국 Google Play 우선, 무료·광고 포함·인앱결제 없음 |
| 기기 범위 | Android 8.0/API 26 이상 스마트폰 우선. 큰 화면과 가로 상태에서도 조작 가능 |
| 게임 분위기 | 따뜻하고 조용한 작은 우주. 방치에 따른 죽음·패널티·출석 압박 없음 |
| 운영 부담 | 초기 자체 게임 서버·고객 계정 관리 없음. 광고 계정·정책·정산 관리는 필요. 후속 서버 비용은 별도 |

게임명은 작업용으로 ‘별 키우기 · ZeroStar’를 쓴다. 최종 명칭·출시 국가·대상 연령·패키지 ID는 사용자 준비 문서에서 확정한다. 연령 등급은 기획자의 희망 숫자가 아니라 실제 콘텐츠와 스토어 설문 결과를 따른다.

## 2. 선택한 게임 방향

| 방향 | 장점 | 비용과 판단 |
| --- | --- | --- |
| 한 번에 별 하나를 키우고 6종 도감 완성 | 화면·재화·저장 구조가 작고 목표가 명확함 | 권장. 짧고 완결된 첫 출시 |
| 여러 별을 동시에 배치하는 우주 정원 | 꾸미기와 장기 수집에 유리 | 배치 편집·카메라·여러 생산원 관리가 필요해 보류 |
| 천문 시뮬레이션·행성 문명 성장 | 깊이 있는 성장 가능 | 규칙·설명·콘텐츠가 커져 제외 |

한 줄 소개: **“잠시 쉬는 동안 자란 별을 만나고, 나만의 여섯 빛깔 별 도감을 완성하세요.”** 실제 천체 진화의 과학적 재현을 표방하지 않는다.

핵심 흐름은 자동 별빛 생산 → 별빛으로 생산력 강화 → 누적 생산량에 따라 외형 성장 → 완성한 별을 도감에 등록 → 다음 별의 생산력 증가다. 연타로 재화를 버는 클릭 게임으로 만들지 않는다. 별을 누르면 짧은 반짝임만 보여준다.

### 첫 실행과 반복 접속

1. 첫 실행 즉시 별씨와 별빛 0, 초당 생산량 1을 보여준다. 가입 화면은 없다.
2. 홈에 ‘별은 앱을 닫아도 자라요. 최대 8시간까지 별빛을 모아요.’를 표시한다.
3. 20초 후 첫 강화가 가능하다. 튜토리얼은 별빛·강화·도감 3개의 짧은 안내로 끝내고 다시 강제하지 않는다.
4. 복귀하면 경과 시간과 지급 별빛을 요약한다. 보상은 저장 성공과 함께 자동 반영하며 ‘확인’은 안내를 닫는 동작이다.
5. 성장이 끝나면 ‘도감에 남기기’를 누른다. 다음 별을 시작할 때 초기화되는 항목과 남는 항목을 먼저 보여준다.
6. 여섯 번째 별까지 등록하면 도감 완성과 엔딩 문구를 보여준다. 완성한 마지막 별을 계속 감상할 수 있으며 추가 자동 생산은 멈춘다.

### 광고 기본안

광고 포함은 사용자 확정 사항이며, 사업자와 형식은 최소 구현을 위한 **AdMob 적응형 배너 1개**를 권장한다. 홈 콘텐츠와 하단 탭 사이의 전용 영역에 놓고 강화·등록 버튼과 떨어뜨려 오클릭을 방지한다. 도감·설정·확인 창에는 노출하지 않는다. SDK가 제공하는 광고 표시는 가리거나 픽셀 그래픽으로 변형하지 않는다.

- 광고 시청에 별빛·배율 보상을 연결하지 않는다. 따라서 기존 경제 수치는 유지한다.
- 광고 로딩은 게임 시작을 막지 않는다. 광고 없음/no-fill·네트워크 오류·요청 불가 상태에서는 광고를 숨기고 게임을 계속한다. 재시도 폭주나 자체 고빈도 새로고침은 하지 않는다.
- Google Mobile Ads SDK와 필요한 동의용 UMP SDK만 추가한다. 미디에이션·별도 분석 SDK는 첫 출시에 넣지 않는다. 구현 시 공식 문서에서 현재 권장 안정 SDK 계열과 호환 버전을 선택한다. [AdMob 시작 안내](https://developers.google.com/admob/android/quick-start)
- 실행마다 UMP의 동의 정보를 갱신하고 필요한 양식을 표시한다. SDK의 `canRequestAds`로 요청 가능 여부를 판단하며, 자체 저장한 동의 Boolean으로 대체하지 않는다. 요청 불가 또는 판단 실패 시 광고를 요청하지 않는다. 필요한 개인정보 선택 진입점을 설정에 제공한다. 비개인화 광고도 동의 처리를 생략하는 근거로 삼지 않는다. [UMP 안내](https://developers.google.com/admob/android/privacy)
- 실제 대상 연령·배포 국가에 맞춰 광고 콘텐츠 등급, 아동 대상/동의 연령 관련 설정을 적용한다. 임의로 전 이용자를 성인으로 간주하지 않는다.
- 개발·자동 테스트는 공식 테스트 광고 ID 또는 등록한 테스트 기기를 사용한다. 실제 광고 클릭을 테스트 절차에 넣지 않는다. [테스트 광고](https://developers.google.com/admob/android/test-ads)
- 게임 진행은 로컬에 저장되지만 광고 SDK가 처리하는 정보는 별개다. SDK·전이 의존성·설정에 따른 수집/공유, 광고 식별자 및 권한을 조사하여 개인정보처리방침과 Play 데이터 보안 신고에 반영한다.

## 4. 게임 규칙과 초기 수치

수치는 출시 전 시뮬레이션과 실제 플레이로 확인할 초기 설정이다. 재미가 검증됐다는 의미는 아니다. 수치만 바꾸는 조정은 에이전트가 근거를 남기고 수행할 수 있지만 재화·성장 단계·과금 구조 추가는 범위 변경이다.

### 재화와 생산

- 재화 이름: 별빛. 보유 별빛 `B`와 이번 별에서 누적 생산한 별빛 `G`를 구분한다.
- 강화 레벨 `L`: 0~30. 도감 등록 수 `C`: 0~6.
- `C < 6`일 때 생산량 `R = (1 + 2 × L) × (1 + 0.25 × C)` 별빛/초.
- 강화 비용: 현재 레벨 `L`에서 `ceil(20 × 1.25^L)` 별빛. 최대 레벨에서는 구매 불가.
- 강화는 `B`만 차감한다. `G`를 차감하거나 별 성장 단계를 되돌리지 않는다.
- 별빛은 `Long`의 1/1000 별빛 단위로 저장하고 표시는 소수점 없이 내림한다. 생산량은 소수점 최대 2자리까지 표시한다.
- 생산은 완전한 1초 단위로 계산한다. 전경의 남은 1초 미만 시간은 다음 계산에 이월한다. 백그라운드 전환에서 버리는 시간은 1초 미만이며 반복 이벤트로 더 버리지 않는다.
- 보유/누적 저장 상한은 각각 `1_000_000_000_000_000` 밀리별빛이다. 곱셈 전에 경과 시간과 증가량을 검증하고 포화 연산으로 오버플로를 방지한다.

### 성장 단계

| 단계 | 누적 `G` 기준(별빛) | 외형 변화 |
| --- | ---: | --- |
| 별씨 | 0 | 작은 빛 점과 눈 |
| 작은 별 | 100 | 별 실루엣 등장 |
| 반짝이는 별 | 1,000 | 크기와 빛 증가 |
| 빛나는 별 | 10,000 | 주변 작은 반짝임 |
| 찬란한 별 | 100,000 | 테두리 광채와 위성 장식 |
| 완성된 별 | 500,000 | 최종 모습과 도감 등록 가능 표시 |

단계는 `G`에서 파생하고 별도 저장하지 않는다. 완성 후에는 강화 버튼을 비활성화한다. 등록 전까지 별빛은 쌓이지만 다음 별에 이월되지 않는다고 안내한다.

### 도감 등록과 다음 별

- 6종 순서: 새벽별, 산호별, 라일락별, 바다별, 노을별, 은하별.
- 같은 성장 실루엣 6개를 공유하되 팔레트와 최종 장식을 달리한다. 기본 도감 데이터는 앱 안의 상수로 둔다.
- 등록은 완성 상태에서만 가능하며 한 트랜잭션으로 처리한다.
- `C=0..4`에서 등록: `C += 1`, `B=0`, `G=0`, `L=0`, 정산 시각을 현재로 변경한다. 새 별에는 등록 보너스가 즉시 적용된다.
- `C=5`에서 등록: `C=6`으로 변경하고 마지막 별의 완성 상태를 보존한다. 생산량은 0, 강화·추가 등록 불가, 엔딩과 완성 도감을 제공한다.
- 전체 초기화는 설정에서 별도 확인을 거쳐 실행한다. 엔딩 직후 강제 초기화는 없다.

### 플레이 속도 검증

계획 수치로 ‘매초 정산하고 살 수 있는 즉시 강화’하는 첫 별을 단순 계산한 결과: 첫 강화 20초, 단계 도달은 100/1,000/10,000/100,000/500,000별빛에서 각각 39/95/346/1,943/8,501초였다. 첫 완성은 약 2.36시간이다. 이는 2026-10-12 PowerShell 계산 결과이며 실제 앱 검증이나 이용자 행동 예측이 아니다.

추가 계산에서는 처음 180초 동안 즉시 강화하고 이후 매 복귀마다 가능한 강화를 수행했다. 완성한 별은 복귀 시 바로 등록하고 다음 별로 넘어갔다. 밤에도 같은 간격으로 복귀하는 가정에서 4시간 간격은 6종 완성까지 44시간 3분(1.84일), 8시간 간격은 88시간 3분(3.67일)이었다. 4시간 간격은 하루 6회인 적극적인 이용에 해당한다.

구현 시 이 세 계산을 테스트로 옮기고 12시간 간격도 확인한다. 목표는 첫 시각 변화 1분 안팎, 첫 복귀의 뚜렷한 성장, 일반적인 하루 2~4회 접속에서 도감 완성 약 3~7일이다. 적극적인 이용자가 더 일찍 완성하는 것은 허용한다. 일반 접속 시나리오가 목표를 벗어나면 수치만 조정하고 표·테스트·결과를 함께 갱신한다. 단순 반복이 지루하다는 피드백은 출시 위험으로 기록하며 미니게임 추가로 해결하지 않는다.

글꼴·음원·그림의 사용 권리와 재배포 라이선스를 확인해 번들에 포함한다. 웹 폰트 CDN 요청은 하지 않는다. 흰 글자를 산호색 버튼 위에 무조건 복사하지 않고 명도 대비를 확인해 잉크색 글자 등을 사용한다. 읽어야 하는 작은 글자에는 최소 4.5:1 대비를 적용한다.

### 화면 3개

1. **홈**: 상단 별빛·초당 생산량 / 중앙 별 관찰 창 / 단계와 다음 목표 / 강화 버튼 / 완성 시 등록 버튼. 별빛·강화가 첫 화면에서 보이도록 한다.
2. **도감**: 2열 6개 카드, 획득 수와 생산 보너스. 완료 카드를 누르면 완성 별과 짧은 설명을 본다.
3. **설정**: 효과음, 움직임 줄이기, 저장 안내, 개인정보·광고 개인정보 선택(필요 시)·라이선스·문의·버전, 초기화.

하단 탭 3개는 Compose 상태값으로 전환한다. 별도의 내비게이션 프레임워크는 필요하지 않다. 복귀 안내·등록 확인·초기화 확인은 다이얼로그를 사용한다.

360dp 폭부터 세로 스크롤로 대응하고 600dp 이상은 중앙 폭 제한을 적용한다. 가로·분할 화면에서도 잘림 없이 스크롤 가능해야 한다. 시스템 상태·제스처 영역을 피한다. 터치 영역 최소 48dp, 글자 배율 1.3배, TalkBack의 버튼 명칭·금액·비활성 이유를 검증한다. 장식은 읽기 대상에서 제외하고 재화 변경을 매초 음성으로 읽지 않는다.

## 6. 기술 선택과 구조

| 대안 | 평가 |
| --- | --- |
| Kotlin + Jetpack Compose | 권장. Android 하나가 목표이며 대부분 패널·버튼과 작은 애니메이션이라 게임 엔진이 불필요함 |
| React + Capacitor | 참고 코드와 언어를 공유할 수 있지만 데스크톱 레이아웃을 다시 만들어야 하고 WebView·플러그인 생명주기 관리가 추가됨 |
| Godot | 실시간 게임·복잡한 장면에는 유리하나 현재 범위에서는 엔진 도입과 내보내기 구성이 추가됨 |

Android 앱 모듈 하나에 순수 Kotlin 게임 규칙, DataStore 저장소 하나, ViewModel 하나, Compose 화면과 작은 광고 연동 코드를 둔다. DI 프레임워크, Room DB, 자체 게임 API 계층, 멀티 모듈, 공용 게임 엔진을 만들지 않는다. 광고 통신은 광고 SDK가 담당하며 게임 저장소와 분리한다. DataStore와 직렬화는 검증된 Android/Kotlin 라이브러리를 사용한다. [Android DataStore 공식 문서](https://developer.android.com/topic/libraries/architecture/datastore)

- `minSdk = 26`, `targetSdk = 36`, `compileSdk >= 36`을 초기 기준으로 삼는다. 2026-10-12 확인한 Google Play 안내는 2026-08-31부터 일반 신규 앱에 API 36 이상을 요구한다. 실제 제출 직전에 다시 확인한다. [대상 API 정책](https://support.google.com/googleplay/android-developer/answer/11926878)
- Kotlin·AGP·Gradle·Compose·JDK 조합은 M0에서 공식 호환표를 확인하고 안정 버전으로 고정한다. 동적 버전과 불필요한 SDK는 금지한다.
- 게임 진행은 인터넷 없이 가능하다. 광고 SDK에 필요한 인터넷·네트워크 상태 권한과 병합 Manifest의 광고 식별자 등 권한을 확인하고 실제 사용·신고와 일치시킨다. 알림·외부 저장소·위치·연락처 권한은 추가하지 않는다. 문의와 정책 링크는 외부 앱으로 연다.
- 16KB 환경에서 실행한다. 직접 작성한 Kotlin 외에도 모든 의존성의 `.so` 포함 여부를 확인한다. Kotlin 앱이라는 이유만으로 전이 의존성 검증을 생략하지 않는다. [16KB 호환성](https://developer.android.com/guide/practices/page-sizes)

## 7. 시간 계산과 저장 계약

저장 데이터: `schemaVersion=1`, `balanceMilli: Long`, `earnedMilli: Long`, `upgradeLevel: Int`, `collectedCount: Int`, `lastSettledEpochMs: Long`, `soundEnabled: Boolean`, `reduceMotion: Boolean`, `tutorialSeen: Boolean`. 별 종류와 단계는 도감 수·누적 생산량에서 파생한다.

### 정산

- 전경에서는 단조 증가 시간으로 경과량을 구해 1초마다 화면만 갱신한다. 실제 재화 정산은 경과 시간 곱셈으로 하며 틱 호출 횟수를 믿지 않는다.
- 30초마다, 강화·도감 등록·설정 변경 시, 백그라운드 전환 시 정산 결과를 저장한다. 종료 콜백만 믿지 않는다.
- 복귀 시 `offlineSeconds = floor(clamp(nowEpochMs - lastSettledEpochMs, 0, 28_800_000) / 1000)`.
- 보상은 이탈 당시 저장된 레벨과 도감 수의 생산량으로 계산한다. 이후 구매나 도감 등록으로 과거 보상을 다시 계산하지 않는다.
- 복귀 지급과 기준 시각 갱신은 하나의 DataStore 갱신으로 처리한다. 복귀 이벤트가 연달아 들어와도 직렬화된 최신 저장 상태를 기준으로 한 번만 지급한다.
- 8시간을 넘긴 시간은 버리고 기준 시각은 현재로 옮긴다. 같은 오래된 구간을 다음 실행에 또 청구할 수 없어야 한다.
- 시각이 과거로 바뀌면 보상 0, 기준 시각은 현재로 재설정한다. 타임존 변경은 epoch 차이에 영향을 주지 않는다.
- 서버가 없으므로 사용자가 기기 시각을 반복 조작하는 치팅을 완전히 막지 않는다. 과금·경쟁이 없는 범위에서 받아들이는 한계다. 향후 경쟁이나 유료 재화 도입 전 재설계한다.

### 원자성과 오류

강화·등록·복귀·초기화는 한 저장소가 직렬 처리한다. 저장에 성공한 다음 성공 UI와 음향을 내보낸다. 연타로 지출·도감 등록이 중복되거나 잔액이 음수가 되어서는 안 된다. 저장 실패 시 기존 영속 상태를 보존하고 구매·등록을 막은 뒤 재시도를 제공한다.

첫 실행의 ‘파일 없음’만 새 게임으로 처리한다. 손상·읽기 오류·지원하지 않는 미래 스키마를 새 게임으로 취급하지 않는다. 원본을 유지하고 오류 화면을 표시하며, 사용자가 명시적으로 선택한 초기화만 별도 수행한다. v1 이전 공개 버전이 없으므로 가짜 마이그레이션 계층은 만들지 않는다. 이후 스키마를 바꾸면 실제 이전 버전 fixture와 변환 테스트를 추가한다.

자동 백업·기기 간 전송에서 게임 저장 데이터를 제외하도록 Android 백업 규칙을 설정하고 플랫폼별 적용을 확인한다. 앱 업데이트는 저장을 유지한다. 삭제·데이터 지우기·기기 변경 시 복구를 보장하지 않으며 설정과 스토어 설명에 명시한다. 첫 출시에는 수동 내보내기·가져오기도 넣지 않는다.

기기 최소 구성: 보급형 또는 4GB급 Android 실기기 1대와 최신 Android 실기기 1대. API 26과 API 36, 16KB 환경은 에뮬레이터로 추가 확인한다. 같은 기기 하나로 두 실기기 항목을 대체하지 않는다. 실제 OS와 모델은 확보한 뒤 기록한다. 에뮬레이터 결과를 실기기 성능 증거라고 부르지 않는다. 성능·메모리·시작 속도는 광고 활성(테스트 광고)과 광고 로드 실패 상태에서 모두 확인한다. SDK 초기화·동의 흐름과 배너 뷰가 Activity를 누수시키지 않아야 한다.

## 9. 출시 준비와 에이전트 중단 조건

### 상태 정의

| 상태 | 의미 |
| --- | --- |
| `IN_PROGRESS` | 구현·검증·자료 작성 중 |
| `TECHNICALLY_READY` | 로컬 기능·품질·빌드 기준 통과. Play 계정 조건까지 완료됐다는 뜻은 아님 |
| `WAITING_FOR_USER` | 계정 인증·서명 키·기기·최종 정보·허가 등 사용자 행동 필요 |
| `WAITING_FOR_EXTERNAL` | 필수 테스트 기간·프로덕션 액세스 심사 등 외부 조건 대기 |
| `RELEASE_READY` | 아래 필수 항목을 전부 충족. 사용자가 출시 제출을 결정할 수 있는 상태 |
| `PUBLISHED` | 실제 공개 완료. 이번 계획의 필수 목표 밖 |

**에이전트의 성공 중단 조건은 `RELEASE_READY`다.** 다음 항목은 AND 조건이며 통과 증거가 없는 항목은 미완료다.

- [ ] 이 명세의 기능·저장·접근성·실기기 품질 기준 충족.
- [ ] 출시 차단 결함 0개. 크래시, 진행 유실, 중복 지급, 핵심 조작 불가, 서명·설치·정책 차단은 차단 결함이다.
- [ ] 확정 패키지 ID, versionCode/versionName, 안전하게 보관된 업로드 키와 사용자 보관 확인.
- [ ] 서명 AAB, 테스트 APK, 파일 해시, 빌드 재현법, 사용 의존성·라이선스, 테스트 결과를 제공.
- [ ] 소스·문서·테스트·빌드 설정이 Git에 커밋되어 있고 릴리스 커밋/태그와 AAB 해시를 연결. 키·암호·기기 데이터가 추적되지 않음.
- [ ] 정확히 그 AAB에서 생성되거나 Play가 배포한 앱을 설치해 핵심 기능 및 업데이트 유지 확인.
- [ ] 내부 테스트 배포 확인과 제공 가능한 Play 사전 출시 보고서 검토. 제공되지 않는 보고서는 이유와 대체 검증을 기록.
- [ ] 스토어명·소개·설명·아이콘·대표 이미지·실제 앱 스크린샷·지원 이메일 준비.
- [ ] 공개 개인정보처리방침 URL 동작 확인, 앱 안에서도 열림. 데이터 보안·광고·앱 액세스·대상 연령·콘텐츠 등급 신고 내용과 실제 구현 일치.
- [ ] ‘광고 포함’ 신고, 실제 광고 앱/단위 ID 설정, 동의/개인정보 선택, 광고 SDK 데이터 처리 및 권한 검증 완료. 광고 계정과 앱 심사·소유 확인·app-ads.txt 등 사업자가 요구하는 배포 선행 조건 충족. 테스트 ID만 연결된 상태는 출시 준비 완료가 아님. 실제 광고가 매 요청 채워지는 것은 합격 조건으로 두지 않음.
- [ ] 출시 국가에 따른 계정·게임 등급·배포 요구 확인, Play Console의 미해결 필수 작업 없음.
- [ ] 해당 계정에 비공개 테스트 및 프로덕션 액세스 승인 조건이 있으면 실제 충족. 단순히 14일이 흘렀다는 것으로 승인 처리하지 않음.
- [ ] `docs/release/RELEASE-READINESS.md`에 항목별 결과·증거 경로·검증 날짜·빌드 해시·잔여 경미 이슈 기록.

사용자나 외부 조건이 막히면 독립적으로 가능한 코딩·테스트·자료 준비를 끝내고, 정확히 필요한 입력과 재개 명령을 남긴다. 이를 성공 완료로 바꾸거나 가짜 증거로 통과시키지 않는다. 대기 기간 동안 세션을 무한 실행하거나 승인 없이 반복 자동화를 만들 필요는 없다. 후속 재개 시 같은 체크리스트부터 이어간다.

실제 공개 배포·결제·법적 동의·신원 인증은 사용자 소유 결정이다. 이번 문서 작성이나 향후 구현 위임만으로 공개 배포까지 승인된 것으로 취급하지 않는다. 코드 수정·검증·자료 작성은 맡겨진 구현 범위 안에서 계속한다.

## 10. 정책 확인 근거

확인 기준일은 2026-10-12다. 계정별 콘솔 안내와 실제 제출일 정책을 다시 확인한다.

- 2023-11-13 이후 생성된 개인 개발자 계정에는 최소 12명의 테스터가 연속 14일 참여한 비공개 테스트 후 프로덕션 액세스를 신청하는 조건이 안내되어 있다. [개인 계정 테스트 요구](https://support.google.com/googleplay/android-developer/answer/14151465)
- 광고 SDK를 포함한 실제 수집·공유 동작으로 데이터 보안 양식과 개인정보처리방침을 작성한다. 게임 서버가 없다는 이유로 ‘수집 없음’을 신고하지 않는다. [데이터 보안](https://support.google.com/googleplay/android-developer/answer/10787469)
- 계정 등록·인증과 등록 시 표시되는 비용은 소유자가 처리한다. [Play Console 시작](https://support.google.com/googleplay/android-developer/answer/6112435)
- 심사 정보와 스토어 시각 자료는 제출 직전 규격으로 검사한다. [심사 준비](https://support.google.com/googleplay/android-developer/answer/9859455?hl=en), [미리보기 자료](https://support.google.com/googleplay/android-developer/answer/9866151)

## 11. 알려진 한계

첫 출시는 6종 완성으로 끝나는 작은 게임이며 장기 라이브 서비스나 광고 매출을 보장하지 않는다. 광고가 표시되지 않는 상황에서도 진행할 수 있다. 초기에는 로컬 저장만 제공하므로 기기 변경 시 진행 복구를 보장하지 못한다. 기기 시각 조작을 완전히 차단하지 않는다. 참고 프로젝트의 실제 실행 화면 비교, Android 빌드 및 실기기 측정은 아직 수행하지 않았다. 구현 단계에서 증거를 채워야 한다.

## 12. 후속 서버 로그인·복구와 Git 보관

사용자 결정에 따라 초기 출시 이후 DB 서버를 활용한 로그인과 진행 복구를 구현한다. 이 후속 작업은 초기 `RELEASE_READY`에 포함하지 않는다. 초기에는 기존의 저장소 경계와 `schemaVersion`만 유지하고 서버, 계정 ID, 동기화 큐, 빈 원격 저장소 구현을 미리 추가하지 않는다.

후속 구현 순서는 인증 방식과 서버 API·DB 설계 → 인증된 계정별 저장/조회 → 최초 로그인 시 로컬 진행의 계정 이전 → 재설치·다른 기기 복구 검증이다. 앱이 DB에 직접 접속하지 않도록 하고, 서버에서 계정별 접근권한을 검사한다. 기존 로컬 진행과 서버 진행이 충돌할 때의 선택·중복 업로드 방지, 저장 스키마 이행, 로그아웃·계정 삭제·데이터 삭제, 서버 장애 시 오프라인 동작을 별도 명세로 확정한다. 백업·복구 훈련과 운영 비용도 이 단계에서 준비한다. 실시간 다기기 동기화까지 자동으로 범위를 확대하지 않는다.

Git 사용은 확정이다. 소스·문서·테스트·빌드 설정·필요한 원본 자산을 추적하고, 빌드 산출물·캐시·local.properties·서명 키·비밀·테스터 식별정보는 제외한다. 구현 시작 단계에서 저장소를 초기화하고 작은 검증 단위로 커밋한다. 릴리스는 커밋/태그와 빌드 해시로 연결한다. 원격 서비스·URL·공개 범위는 사용자 준비 사항이며 비공개를 권장한다. 원격이 준비되기 전에는 로컬 Git으로 진행하고, 연결을 위임받은 원격에만 push한다. 단순 로컬 Git을 원격 백업 완료로 보고하지 않는다.
